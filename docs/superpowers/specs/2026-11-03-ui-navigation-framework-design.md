# UI 主界面导航与交互框架设计

> 日期：2026-11-03  
> 状态：设计已确认，等待书面规范复核  
> 项目：InfiniteEvolutionDoomsdaySurvival  
> 引擎：Cocos Creator 3.8.8 + Oops Framework

## 1. 背景与目标

项目当前已经具备 `Loading → Hall → Battle` 的占位链路，以及 Oops Framework 的 UI 分层和资源加载能力，但 Hall 仍由脚本临时绘制标题与按钮，没有稳定的页面导航、返回策略、通用页面生命周期和弹窗交互。

本阶段建立可持续扩展的 UI 基础，并完成第一个可操作闭环：

1. 启动进入方舟主界面。
2. 主界面六个功能入口均可进入和返回。
3. “出发”进入战斗 HUD 占位界面。
4. 战斗界面支持暂停、继续和确认返回方舟。
5. 全屏页面、覆盖层与确认弹窗遵循统一返回规则。

本阶段不实现装备、制造、建设、研究、成员和情报的完整业务规则，也不实现实际战斗逻辑。

## 2. 已确认方案

采用“独立页面 Prefab + 统一导航服务 + Oops UI 分层”方案。

- 每个功能页面拥有稳定的 `UIID` 和独立 Prefab。
- 首阶段功能页面复用统一结构和视觉组件，但保留独立 ViewModel 与替换边界。
- `UINavigationService` 维护逻辑页面栈、覆盖层和切换锁。
- Oops GUI 继续负责资源加载、实例化、缓存和 UI 层级。
- 全屏页面切换时移除旧页面；需要保留状态的页面使用 `destroy: false` 缓存。
- 不采用单个 Hall Prefab 内大量节点显隐，也不继续把正式 UI 全部动态绘制在 TypeScript 中。

## 3. 页面结构

### 3.1 启动与根页面

```text
Loading
  └─ Hall（方舟主界面，页面栈根）
```

Hall 展示：

- 章节、天数和当前阶段。
- 废料、合金、能源等首阶段演示资源。
- 方舟核心耐久、能源和威胁摘要。
- 装备、工坊、建设、研究、成员、情报六个功能入口。
- 高权重“出发”按钮。

### 3.2 功能页面

```text
Hall
  ├─ Equipment（装备与仓库）
  ├─ Workshop（工坊制造）
  ├─ ArkBuild（方舟建设）
  ├─ Research（研究与进化）
  ├─ Crew（成员与岗位）
  └─ Intel（地图、任务与尸潮情报）
```

首阶段每个页面提供：

- 页面标题和系统图标。
- 一段简短功能说明。
- 与该模块相关的演示状态卡片。
- 明确的返回按钮。

这些页面的业务数据来自集中式演示 ViewModel，不写死在 Prefab 或按钮回调中。

### 3.3 战斗 HUD 与覆盖层

```text
Hall ──出发──> BattleHUD
                  ├─ PauseOverlay
                  └─ ReturnConfirmDialog ──确认──> Hall
```

BattleHUD 首阶段包含玩家状态、昼夜进度、目标提示、暂停按钮和返回方舟入口。它只验证 UI 交互和导航，不生成玩家、敌人或战斗结算。

PauseOverlay 是覆盖层，支持继续和返回方舟。返回方舟必须经过 `ReturnConfirmDialog`；取消确认后保持当前战斗 HUD。

## 4. 导航与返回规则

### 4.1 页面栈

- Hall 是页面栈根。
- 打开功能页执行 `push(route, params)`。
- 返回执行 `pop()`，恢复上一页。
- Hall 到 BattleHUD 使用 `replace(route, params)`，防止普通返回重新暴露 Hall。
- BattleHUD 确认退出后清理战斗相关页面并重建 Hall 根状态。
- 栈底 Hall 收到普通返回请求时安全无操作。

### 4.2 覆盖层

- 暂停、确认框和通用提示位于当前全屏页面之上。
- 返回键优先关闭最上层确认框，其次关闭暂停层，最后处理全屏页面。
- 进入新阶段时清理不再有效的临时覆盖层。
- 覆盖层不写入全屏页面栈。

### 4.3 并发与失败恢复

- 页面切换期间启用导航锁；重复点击或重复打开当前页面直接忽略。
- 目标 Prefab 加载成功后才移除原页面，避免出现空白屏幕。
- 加载失败时解除导航锁、保留原页面并显示可理解的提示。
- 非法路由、空栈返回和重复关闭均为安全无操作，同时在开发环境输出诊断信息。

## 5. 组件边界

### `UIRoute`

集中定义页面 ID、Prefab 路径、Oops 层级、缓存策略和返回策略。业务页面不得在代码中散落资源路径。

### `UINavigationService`

负责：

- 页面栈和当前路由。
- `push`、`pop`、`replace` 和返回请求。
- 覆盖层注册和关闭顺序。
- 切换锁、重复导航保护和失败恢复。

它不保存装备、资源、角色或战斗业务状态。

### `GamePage`

统一页面组件基类，负责：

- 接收导航参数。
- 绑定通用返回按钮。
- 注册和解绑全局事件。
- 页面退出和销毁清理。

### 页面组件

- `HallViewComp`：渲染方舟主页状态并提交导航意图。
- 六个功能页组件：消费各自 ViewModel，不直接引用 Hall。
- `BattleHUDViewComp`：维护 HUD 占位交互和暂停意图。
- `PauseOverlayViewComp`：继续或请求返回方舟。
- `ConfirmDialogViewComp`：通过回调或结果事件返回确认结果。

## 6. 数据流

```text
触控输入
  → 页面组件
  → UINavigationService / GameEvent
  → Oops GUI
  → 新页面组件
  → ViewModel 渲染
```

- 页面间不直接持有彼此的组件引用。
- 真实业务模块以后通过 ViewModel、查询接口和 `GameEvent` 接入。
- 首阶段的章节、资源、方舟和功能页状态统一放在演示数据源中。
- 演示数据的字段名与后续业务含义一致，替换数据源时不要求重做 Prefab 结构。

## 7. 视觉与适配

- 设计基准为 1334×750 横屏。
- 支持 16:9、18:9、19.5:9 和 20:9；关键按钮位于安全区内。
- 延续深蓝黑面板、科技青描边、高对比白色图标和警戒橙主操作色。
- 复用现有 P0 UI 组件、系统导航图标、方舟底盘和模块素材。
- 概念效果图只作为布局与层级参考，不把整张效果图直接用作可交互背景。
- 面板和按钮使用九宫格；图标与文字由原生节点叠加。
- 像素素材使用最近邻采样，避免非整数缩放。
- 可见按钮与触控热区分离；主要按钮扩展 10–16 个设计单位的点击范围。

## 8. 异常与生命周期处理

- Prefab 缺失：保留原页、提示失败、释放导航锁。
- 页面重复打开：忽略请求，不产生第二个实例。
- 页面退出：统一解绑按钮和全局事件。
- 页面销毁：不得保留定时器、异步回调或失效节点引用。
- 异步加载完成时若请求已失效，不再切换页面。
- BattleHUD 退出时清理暂停层和确认框，避免覆盖层带回 Hall。

## 9. 验收标准

### 功能验收

1. 冷启动稳定完成 `Loading → Hall`。
2. Hall 六个功能入口均能进入正确页面并返回 Hall。
3. “出发”能进入 BattleHUD。
4. BattleHUD 的暂停、继续和返回方舟确认均有效。
5. 取消返回确认后仍保持原 BattleHUD 状态。
6. 返回键始终只处理当前最上层页面或覆盖层。
7. 连续快速点击不会创建重复页面或破坏页面栈。

### 稳定性验收

1. 每个功能页连续进入退出 20 次，无重复监听和失效节点错误。
2. Hall 与 BattleHUD 往返 20 次，页面栈和覆盖层均恢复到确定状态。
3. 人为配置无效 Prefab 时，原页面仍可操作且导航锁自动解除。

### 适配与视觉验收

1. 16:9、18:9、19.5:9 和 20:9 下关键按钮不越出安全区。
2. 主要入口、返回、暂停和确认按钮的触控热区符合移动端尺寸要求。
3. UI 色彩、描边、图标和面板风格与现有主玩法效果图一致。
4. 不使用整张概念 UI 图冒充正式交互界面。

## 10. 实施边界

本设计完成 UI 框架与交互闭环，不包含：

- 实际装备、制造、建设、研究和成员管理规则。
- 战斗角色、敌人、伤害、掉落和结算。
- 正式存档、平台登录、广告或支付。
- 最终多语言文案和发布级美术验收。

后续功能按独立页面逐步接入业务 ViewModel，不改变导航服务和页面生命周期约定。
