# 研究与进化可玩闭环设计

> 日期：2026-11-08
>
> 状态：方案已确认，等待书面规范复核
>
> 项目：InfiniteEvolutionDoomsdaySurvival
>
> 引擎：Cocos Creator 3.8.8 + Oops Framework

## 1. 背景与目标

当前 `Research` 页面由通用 `FeaturePageViewComp` 动态绘制，只展示演示指标和固定倒计时；“开始研究”按钮绑定空回调。项目没有研究定义、运行时状态、队列、完成结算、存档或战斗属性接入，因此任何可见操作都不会改变游戏。

本阶段把研究页替换为完整可玩闭环：

1. 玩家能在机械、生存、生化、混合四类研究中选择节点。
2. 节点具有稳定 ID、研究点成本、前置节点、研究时间、永久收益和可选生化负荷。
3. 研究队列最多容纳 3 项，按顺序执行；退出页面或关闭游戏后继续按真实时间结算。
4. 研究完成状态和剩余研究点写入本地存档。
5. 已完成研究真实改变战斗中的最大生命、最大护盾、攻击伤害和移动速度。
6. 研究业务规则由纯 TypeScript 模型承担，Cocos 页面只负责输入、渲染与生命周期。

本阶段不重做全局经济、云存档、账号同步、正式数值平衡或完整章节奖励系统。

## 2. 引擎集成契约

| 契约 | 项目证据与本阶段绑定 |
|---|---|
| 构建与运行 | `package.json` 固定 Cocos Creator `3.8.8`；用 Creator 打开工程并运行 `main` 场景。自动验证沿用 Node 22+ 的 `node --test` 与 TypeScript 直接导入。 |
| 生命周期 | 页面继承 `GamePage`；`onLoad/start` 创建界面，`update(deltaTime)` 刷新倒计时，`onDestroy` 通过基类解绑触控。本阶段新建专用 `ResearchViewComp`，不改变导航栈。 |
| 时间与输入 | 页面触控通过 `GamePage.bindTouch` 绑定；研究完成时间使用注入的毫秒时钟，不依赖页面 `deltaTime`，因此页面关闭和离线期间仍可结算。 |
| 状态与资源 | 研究定义是不可变内容数据；研究点、已完成节点和队列是可变存档状态。节点引用稳定字符串 ID，不保存 Cocos `Node` 或组件引用。 |
| 持久化 | 生产适配器使用 `oops.storage.getJson/set`；研究模型仅依赖 `ResearchStorage` 接口，单元测试使用内存适配器。 |
| 战斗接入 | `BattleHUDViewComp` 创建 `BattleSimulation` 时传入由已完成研究汇总出的 `BattlePlayerModifiers`；模拟器负责把修正应用到玩家生命、护盾、攻击伤害和移动速度。 |

## 3. 方案边界与组件

### 3.1 `ResearchCatalog`

集中保存研究节点定义并提供按 ID、分类和层级查询。定义字段为：

```ts
interface ResearchDefinition {
    id: string;
    branch: "mechanical" | "survival" | "biochemical" | "hybrid";
    tier: 1 | 2 | 3;
    name: string;
    description: string;
    cost: number;
    durationSeconds: number;
    prerequisites: readonly string[];
    effects: readonly ResearchEffect[];
    bioLoad?: number;
}
```

目录加载时验证 ID 唯一、成本和时长为正数、前置存在、没有自依赖或循环依赖。无效目录在开发阶段直接抛出可定位错误，不进入运行时页面。

### 3.2 `ResearchRuntime`

纯 TypeScript 业务模型，负责：

- 加载、迁移和归一化研究存档。
- 查询节点的 `locked`、`available`、`queued`、`researching`、`completed` 状态。
- 原子验证并提交研究：检查节点存在、未完成、未入队、前置完成、研究点足够、队列未满；全部通过后才一次性扣点并入队。
- 使用绝对完成时间顺序执行队列。
- 结算在线和离线期间完成的所有节点，并立即推进后续队列项。
- 汇总永久属性修正和生化负荷。
- 每次有效状态变化后写入存档。

模型的公开命令返回结构化结果，不通过异常表达玩家可预期的失败：

```ts
type StartResearchResult =
    | { ok: true; entry: ResearchQueueEntry }
    | { ok: false; reason: "unknown" | "completed" | "queued" | "prerequisite" | "points" | "queue-full" };
```

### 3.3 `ResearchStorage`

存档采用版本化结构：

```ts
interface ResearchSaveV1 {
    version: 1;
    points: number;
    completed: string[];
    queue: Array<{ nodeId: string; finishAtMs: number }>;
    lastObservedAtMs: number;
}
```

- 新档默认 8 点研究点，足够体验多个浅层节点但不能点满全部路线。
- 队列保存绝对 `finishAtMs`，后续项目即使调整节点时长，也不会改变已经开始的研究。
- 加载时丢弃不存在、重复或已完成的队列项，并把点数钳制为非负整数。
- 若设备时间倒退，结算使用 `max(now, lastObservedAtMs)`，不倒扣进度，也不凭倒退时间重复获得完成结果。
- 存档解析失败时保留原始键值并回退到新档，同时输出诊断；不让损坏存档阻塞进入页面。

### 3.4 `ResearchModifiers`

研究效果仅使用明确的可组合类型：

```ts
type ResearchEffect =
    | { stat: "maxHealth"; add: number }
    | { stat: "maxShield"; add: number }
    | { stat: "attackDamage"; multiplier: number }
    | { stat: "moveSpeed"; multiplier: number };
```

加法效果先累加，乘法效果相乘；最终修正在独立纯函数中汇总。战斗模拟器收到的是汇总结果，不读取研究存档，也不认识节点 ID。

### 3.5 `ResearchViewComp`

`UIID.Research` 从通用 `FeaturePageViewComp` 注册切换为专用页面组件。页面继续复用现有 `research.prefab` 根、`UIBuilder`、安全区、返回按钮和纹理风格。

页面结构：

- 左侧：机械、生存、生化、混合四个分类按钮，显示分类完成数。
- 中间：当前分类的 3 个层级节点；节点显示图标、名称、成本和状态，并用连线/锁标识前置关系。
- 右侧：选中节点的说明、永久收益、前置条件、生化负荷和“开始研究”按钮。
- 底部：3 个顺序队列槽；首项显示“进行中”和秒级倒计时，其余显示“等待中”与预计完成时间。
- 顶部指标：当前研究点、可研究节点数、生化负荷。

交互规则：

- 打开页面时先执行一次离线结算，再渲染当前状态。
- 点击节点只改变选中项，不扣除资源。
- 点击“开始研究”提交命令；成功后刷新全页，失败时在按钮上方显示对应原因。
- 已完成、研究中和等待中的节点不能重复提交。
- `update` 仅在显示秒数变化或研究完成时刷新，避免每帧重建节点树。
- 离开页面后不需要保留定时器；下一次查询或进入战斗时由运行时按绝对时间自动结算。

首批共 12 个节点，每条路线 3 个层级。时间保持在原型阶段可快速验证的 20–90 秒，后续可只改目录数据，不改业务代码。

## 5. 队列与离线结算

队列是单工作位、三槽等待队列，而不是三项并行研究：

1. 首项的 `finishAtMs = effectiveNow + duration`。
2. 后续项的 `finishAtMs = previous.finishAtMs + duration`。
3. 每次 `reconcile(now)` 从队首开始完成所有 `finishAtMs <= effectiveNow` 的节点。
4. 一次离线跨过多个完成时间时，按队列顺序一次性完成所有到期节点。
5. 完成不会返还研究点；队列项开始时即已扣费。
6. 本阶段不支持取消，避免“正在研究时退款比例”和后续依赖失效产生未定义规则。

前置节点必须已经完成才能入队，不能仅依赖同一队列中的前序项。这样状态判定保持简单、失败提示明确，也避免取消功能加入后破坏依赖链。玩家可在前置完成后再提交下一层节点。

## 6. 数据流

```text
本地存档
  → ResearchStorage
  → ResearchRuntime.reconcile(now)
  → ResearchViewComp 查询状态并渲染
  → 玩家选择节点并提交 startResearch(id, now)
  → 原子校验 / 扣点 / 入队 / 保存
  → 页面刷新倒计时

进入战斗
  → ResearchRuntime.reconcile(now)
  → 汇总 ResearchModifiers
  → new BattleSimulation(map, modifiers)
  → 玩家生命 / 护盾 / 伤害 / 移速使用研究后数值
```

研究页不直接操作 `BattleSimulation`；战斗页不直接读取存档。两者只共享研究运行时公开查询和稳定的修正值结构。

## 7. 错误处理

- 未知节点或损坏目录：开发错误，目录验证报告具体 ID。
- 前置未完成、研究点不足、重复研究、队列已满：玩家可预期结果，不修改任何状态并显示中文原因。
- 存档字段缺失或类型错误：归一化可恢复字段，无法恢复时创建新档并记录诊断。
- 页面被销毁：所有触控由 `GamePage` 解绑；研究进度由绝对时间保存，不依赖残留回调。
- 属性修正异常：目录验证拒绝非有限数、非正乘数；模拟器仍为战斗基础配置提供默认值。

## 8. 测试设计

### 8.1 研究模型单元测试

- 节点目录拒绝重复 ID、未知前置和循环依赖。
- 前置、点数、重复项和队列容量分别阻止提交，且失败时点数与队列完全不变。
- 成功提交只扣一次研究点，并计算正确的顺序完成时间。
- 在线时间推进完成首项并保留后续项。
- 离线跨越多个完成时间会按顺序全部结算。
- 设备时间倒退不会减少进度或重复完成。
- 损坏存档归一化后不包含未知或重复节点。
- 属性修正按加法累加、乘法相乘，并忽略未完成和仅在队列中的节点。

### 8.2 战斗集成测试

- 无研究修正时保持现有基础生命 420、护盾 180、伤害 35、移速 270。
- 传入修正后，玩家实际生命、护盾、攻击伤害和移动速度改变。
- 研究修正只作用于玩家，不改变敌人或场景结构数值。

### 8.3 UI 集成检查

- `UIID.Research` 注册到专用 `ResearchViewComp`，其他五个通用功能页不受影响。
- 研究页包含四个分类、节点状态、3 个队列槽、详情面板和有效主按钮绑定。
- 连续进出研究页不会重复监听或创建第二个运行时状态。
- Node 测试全绿后，再在 Cocos Creator 中执行：入队、退回方舟、重新进入、关闭重开、等待完成、进入战斗查看属性。

## 9. 验收标准

1. 新档显示 8 点研究点和 12 个研究节点。
2. 无前置的节点可以提交；不满足条件的节点明确说明原因且不扣点。
3. 最多保存 3 个研究任务，首项倒计时、后续等待顺序和预计时间正确。
4. 关闭页面或游戏后，重新进入会按真实经过时间完成到期研究。
5. 已完成节点永久显示完成且不能重复研究。
6. 生化节点完成后，生化负荷按节点配置累计并在研究页显示。
7. 完成对应节点后进入战斗，生命、护盾、攻击伤害或移动速度与基础值相比发生可验证变化。
8. 研究状态能跨页面与进程重启保存；损坏数据不会阻塞启动。
9. 新增研究测试、现有战斗测试和 UI 测试全部通过。

## 10. 明确不包含

- 研究点的正式探索掉落、任务奖励或章节结算来源。
- 队列取消、加速、广告缩时、付费内容或联网校时。
- 云存档、账号冲突合并和跨设备同步。
- 生化负荷带来的污染惩罚、净化设施或结局分支。
- 研究树最终美术图标、音效与发布级数值平衡。

这些功能以后通过稳定节点 ID、版本化存档和 `ResearchEffect` 扩展，不要求重写本阶段的队列与状态机。
